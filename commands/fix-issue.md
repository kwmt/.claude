# Fix Issue（issue の確認 → 修正 → ドラフト PR。必要なときだけエージェントに委譲）

## Phase 1: Issue確認
1. `gh` コマンドで $ARGUMENTS（URLまたはissue番号）の内容を、コメントも含めて確認する
2. issueの種類（バグ修正、機能追加、リファクタリング等）・規模・影響範囲を把握する
3. 次のどれかに当たるなら、ブランチも PR も作らずにここで止め、何が分かれば進められるかを
   報告する（憶測で実装しない）。
   - 何を変えればよいのか、どうなれば完了なのかを issue から読み取れない
   - 仕様を確かめる質問が issue に残っていて、まだ答えが付いていない
   - issue がすでに close されている、または対応する PR がすでにある

## Phase 2: ブランチ
- 現在のブランチが main, staging, develop のいずれかなら、そこから作業ブランチを作る
  （ユーザーに確認せずに進める）。名前は `<type>/<要約>-<issue番号>`。type は fix / feat /
  refactor / docs / chore から選ぶ（例: `fix/coupon-percent-range-12`）。プロジェクトに
  ブランチ名の規約があれば、そちらに従う。
- それ以外のブランチにいるなら、新しいブランチは作らず、そのブランチで作業する。
- 作業ツリーに無関係な未コミットの変更があっても、捨てたり stash したりしない。
  そのまま持ち越し、コミットには含めない。

## Phase 3: 進め方を決める（自分で進めるか、委譲するか）
既定ではエージェントを起動せず、メインセッションが自分で調査・実装・確認を行う
（CLAUDE.md の Agent Team Rules と同じ基準）。変更が 1〜2 ファイルに収まり、原因や
やることが issue から読み取れるなら、委譲しない。

委譲するのは、次のどれかに当たるときだけ。当たる役割だけを、必要な数だけ起動する。
- **調査（researcher）**: 原因の当たりがつかず、広い範囲のコードを探索しないと特定できない
- **実装（implementer）**: 独立した複数のモジュール / 複数のファイルを並行して実装できる
- **テスト（tester）**: 実装とは別に、まとまった量のテストを書く必要がある
- **レビュー（reviewer）**: 差分が大きい、またはセキュリティ・パフォーマンス上のリスクが高い

どちらにしたかと、その理由を、最後の報告に 1〜2 行で書く。

## Phase 4: 実行
- **自分で進める場合**: 原因・影響範囲の確認 → 修正 → 修正を確かめるテストの追加・更新 →
  プロジェクトのテスト / lint の実行 → コミット、の順に進める。
- **委譲する場合**: タスクリストを作り、依存関係（調査 → 実装 → レビュー）に沿って割り当てる。
  各エージェントの完了を待ち、結果を次の担当に橋渡しする。同じファイルを複数のエージェントに
  同時に書き換えさせない。

## Phase 5: PR作成
1. 修正完了後、作業ブランチを push し、`/pr` の手順でドラフト PR を作成する。
   ベースは作業ブランチの分岐元（分からなければリポジトリの既定ブランチ）。
2. PR本文に、issueをcloseする記法を 1 行入れる
   - issue が PR と同じリポジトリにある場合: `close #<issue番号>`
     （$ARGUMENTS がURLでも、番号を取り出してこの形にする）
   - issue が別のリポジトリにある場合: `close <owner>/<repo>#<issue番号>`

## 注意事項
- ブランチ名・コミットメッセージ・PR タイトル・PR 本文の書式は、項目ごとに決める。
  プロジェクトの文書（CONTRIBUTING.md、PR テンプレートなど）がその項目を名指しで
  定めていれば、そちらに従う。定めていない項目は、このコマンドと `/pr` の書式に従う
  （例: コミットメッセージの規約しか無いプロジェクトでは、コミットはその規約、PR タイトルは
  `/pr` の書式）。`/pr` が参照する PR テンプレートがリポジトリに無ければ、本文は
  「概要 / 変更内容 / テスト」の構成で書く。
- `http://localhost:8080` のport変更はコミットしないこと
