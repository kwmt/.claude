# self-review-loop — 重大な指摘が 0 になるまで回す

self-review を**修正込みのループに載せた版**。「指摘を出す」で終わらず、
**指摘の真偽を判定 → 直す → 検証 → コミット → 再レビュー**を、対象 severity の指摘が 0 になるか、
打ち切り条件に当たるまで繰り返す。

指摘の一覧が欲しいだけなら `/self-review`。人手レビューに出せる状態まで持っていきたいならこちら。
委譲ポリシー上の位置づけは `~/.claude/skills/self-review/SKILL.md` の冒頭に従う。

## ゴールを「指摘 0」に置くことの危険

先に書いておく。**指摘 0 を目的にすると、目的が「良いコードにする」から
「レビューアを黙らせる」にすり替わる**。誤検知を潰すための無意味な書き換え、指摘箇所ごと
コードを消す回避、ラウンドを重ねるうちのスコープ膨張が起きる。

だから**カウントするのは「残った指摘の数」ではなく「未処理の指摘の数」**。
誤検知や意図的な設計判断は、直さずに **dismiss（理由付きで却下）** して 0 に数える。
これが成立するために §1-2 の分類と §3 の却下理由の記録が要る。

## 0. 開始前の準備

1. **`~/.claude/skills/self-review/SKILL.md` を Read する。** このスキルは self-review の
   §0〜§2 を内側で使うが、self-review は `disable-model-invocation: true` のため Skill ツール
   では呼び出せない。ファイルを読んで手順に従う。
2. **現在の変更をコミット済みにする**。このスキルはレビュー起因の修正をラウンドごとに
   コミットする（§1-5）ので、元の実装が未コミットのまま残っていると、そのコミットに元の実装まで
   巻き込む。未コミットの変更があれば、先にコミットするか確認する。
   `main` / `develop` / `staging` 上にいるなら、コミットする前に作業ブランチを切る
   （保護ブランチに直接コミットしない）。
3. **PR 番号を渡された場合は、その head ブランチをチェックアウトする**（`gh pr checkout <PR>`）。
   このスキルはローカルのワーキングツリーを書き換えるので、対象がリモートにしか無いと
   修正の適用先が無い。チェックアウトしたくないならユーザーに確認する。以降は
   ローカルブランチとして扱う。
4. **引数を解釈する**:
   - `--until=blocker` → blocker のみ 0 にする（速いが甘い）
   - `--until=major`（既定） → blocker と major を 0 にする
   - minor / nit は**停止条件に含めない**。ここまで追うと収束せず、好みの範囲の指摘で差分が
     膨らむ。最後に一覧として報告するに留める。
   - `--max-rounds=N`（既定 4）
5. **開始時点を控える**: `git rev-parse HEAD` と `git diff --shortstat origin/<base>...HEAD`。
   前者は §3 の「レビュー起因のコミット」の差分を出すため、後者は打ち切り条件 6 の判定基準になる。
   ラウンドごとのコミット（§1-5）で HEAD は進むので、**以降は `HEAD` ではなく控えた SHA を使う**。
   §3 の差分は `git diff --stat <控えた SHA>` で出す（コミット済み・未コミットの修正を両方含む。
   `git add -N` 済みなら新規ファイルも含まれる）。

## 1. ラウンドの回し方

各ラウンドは レビュー → 判定 → 修正 → 検証 → コミット の 5 段。

### 1-1. レビュー

**ラウンド 1**: self-review の §0〜§2 を実行し、重複排除・信頼度フィルタを通した**確定指摘**を得る。

**ラウンド 2 以降は、原則 subagent を再起動しない。** 見る対象は「自分がさっき入れた修正」で、
それを subagent に検証させるのは CLAUDE.md が禁じている「自分の作業の検証・ダブルチェックを
目的としたサブエージェント」そのものにあたる。メインループが自分で、前ラウンドで fix に分類した
指摘それぞれについて該当箇所を Read し、直っているか・修正がデグレを生んでいないかを確認する。

再起動してよいのは、修正が self-review §0-3 の委譲基準（差分が大きい、またはセキュリティ・
パフォーマンス上のリスクが高い）を単独で満たすほど大きくなった場合だけ。そのときは
前ラウンドで指摘が出た観点 + 🔒 セキュリティ + ✨ 正しさ / コード品質 に絞る。

**差分スコープは self-review §0-1 から差し替える**（再起動の有無に関わらず）。
self-review は三点 diff（`git diff origin/<base>...HEAD`）や `gh pr diff` を使うが、
前者は**コミット済み**、後者は **push 済み**の内容しか見ない。このスキルは push しないので
`gh pr diff` では修正が永久に見えず、三点 diff でも §1-5 でコミットする前の修正
（検証に失敗して直している途中など）は見えない。どちらでも同じ指摘が再提出されて収束しない。
必ずこちらを使う:

```
git diff $(git merge-base origin/<base> HEAD)
```

（二点 diff。merge-base 起点なのでベース側の進行を巻き込まず、コミット済み・未コミットの修正を両方含む。）

**修正で新規ファイルを作ったら、diff を取る前に `git add -N <file>` する。**
untracked のままだと `git diff` に一切現れず、再レビューのスコープからも §3 の差分統計からも
丸ごと漏れる（新規ファイルにバグを入れても永久に気づけない）。

**判断済みの事項を引き継ぐ**: dismiss と defer に分類した指摘の一覧（file:line と理由）を
ラウンドをまたいで持ち回る。**defer を引き継がないと、既存の課題が毎ラウンド「未処理」として
数え直され、永久に収束しない**。subagent を起動する場合はこの一覧をプロンプトに入れ、
「判断済みなので同じ指摘を再提出しない。ただし理由が誤っていると考える根拠が新たにあるなら、
その根拠を添えて再提出してよい」と伝える（黙って握り潰すのではなく、反論の余地は残す）。

### 1-2. 判定 — 直すか、却下するか

確定指摘を 1 件ずつ、**直す前に**次のどれかに分類する。ここを飛ばして片端から直すと、
誤検知への対応でコードが壊れる。

| 分類 | 条件 | 扱い |
|---|---|---|
| **fix** | 実際に問題で、この変更の責任範囲にある | 直す |
| **dismiss: 誤検知** | 該当ファイルを Read して確認した結果、問題ではない | 直さない。**何を確認して問題でないと判断したか**を記録 |
| **dismiss: 意図的** | ユーザーの指示・既存の設計判断として、そうなっているのが正しい | 直さない。**どの指示 / 判断に基づくか**を記録 |
| **defer: 範囲外** | 実際に問題だが、今回の変更が持ち込んだものではない（既存の課題） | 直さない。報告に「既存の課題」として分離して載せる |

**subagent が古い前提で読んでいないかを疑う**。未コミットの設定変更、別ブランチにしかない
ファイル、まだ push していないコミットなどを見落として誤検知することがある。
判断がつかない blocker は**ユーザーに聞く**。勝手に dismiss しない。

`defer` を認めているのは、既存コードの問題まで直し始めると差分が肥大して、
本来レビューされるべき変更が埋もれるため。

分類結果は**ラウンドごとに記録して持ち回る**（file:line / severity / summary / 分類 / 理由）。
§2 の打ち切り条件 3・4 はラウンド間の比較でしか判定できないので、記録が無いと判定不能になる。

### 1-3. 修正

- fix に分類した指摘だけを直す。
- **指摘の file:line だけを見て機械的に直さない**。なぜその指摘が出たかを理解してから直す。
  同じ原因が他の箇所にもあるなら、そこも直す（defer の基準は守る）。
- 修正はメインループが自分で行う。**修正のためにサブエージェントを起動しない**
  （並列で同じワーキングツリーを書き換えると競合するし、修正には会話の文脈が要る）。

### 1-4. テストを実際に走らせる

**再レビューで指摘が消えたことを確認する前に、コードが動くことを確認する。**
レビューは静的な読みなので、修正がビルドを壊していても指摘は減ってしまう。

- プロジェクトのテスト / lint / 型チェック / ビルドを**実際に実行する**
  （コマンドは README・CI 設定・`package.json` の scripts 等から見つける）。
  これは CLAUDE.md が禁じている「念のための自己検証ステップ」ではなく、実テストの実行にあたる。
- 見つからなければ、その旨を報告に書く（「検証コマンドが特定できなかった」）。
- 失敗したら、次のラウンドに進む前にここで直す。

### 1-5. コミット

検証が通ったら、**そのラウンドで直した分をコミットする**。`commit` スキルを呼び、その手順
（ファイル単位の staging・gitmoji・「なぜ」を本文に書く）に従う。

- **1 ラウンド = 1 コミットを基本にする**。本文には、どの指摘（file:line / severity / 要旨）を
  どう直したかを書く。指摘の由来がコミットに残ると、後から「なぜこの変更が入ったか」を追える。
  意図が明確に分かれる（例: セキュリティ修正とリファクタ）なら `commit` スキルの基準で分ける。
- **検証（§1-4）が通っていない状態ではコミットしない**。失敗したら直してからここに来る。
- fix が 0 件（全て dismiss / defer）のラウンドはコミットしない。
- dismiss / defer した指摘はコミットに書かない。それは §3 の報告に載せる。
- **前ラウンドのコミットへ `--amend` しない**。ラウンド単位で revert できるようにしておく。
- **push はしない**。PR を更新するかはユーザーが決める。

## 2. 打ち切り条件

次のいずれかに当たったら**ループを止めてユーザーに報告する**。粘っても良くならない。

1. **収束**: 対象 severity の未処理指摘が 0 になった（成功）
2. `--max-rounds` に到達した
3. **同じ指摘が再提出された**: 前ラウンドで fix したはずの指摘が同じ内容で戻ってきた。
   修正が効いていないか、レビュースコープが修正を見ていない（§1-1 の差し替えを忘れていないか
   まず確認する）
4. **振動**: 修正が、同 severity の新しい指摘を生むのが 2 回続いた。
   設計レベルの問題を局所修正で潰そうとしているサイン
5. **判断がつかない blocker が残った**: ユーザーに聞くべきものが残っている
6. **差分が膨らんだ**: §1-1 の diff の `--shortstat` の追加行数が §0-5 で控えた値の 2 倍を超えた。
   スコープが膨らんでいる

2〜6 は失敗ではなく**中断**。そこまでに直したものと、残っているものを正直に報告する。

## 3. 報告

ループが終わったら、次を報告する。ラウンドごとの実況は要らない（結果だけでよい）。

```
## 結果
<収束した / 打ち切った（理由）>  ラウンド数: N

## 直したもの
- <file:line> <severity> <指摘の要旨> → <どう直したか>

## 却下したもの
- <file:line> <severity> <指摘の要旨> → <却下の分類と理由>

## 既存の課題として残したもの（defer）
- <file:line> <severity> <指摘の要旨>

## 残っている指摘
- <blocker/major が残っているなら、なぜ残ったか>
- <minor / nit の一覧。停止条件には含めていない旨を添える>

## 検証
- <実行したコマンドと結果。特定できなかった場合はその旨>

## レビュー起因のコミット
- <SHA> <件名>（ラウンド N）
- <§0-5 で控えた SHA からの差分の統計。未コミットの変更が残っていればその旨>
- push はしていない
```

**却下したものを必ず載せる**。ここが隠れると「指摘 0」が信用できなくなる。
ユーザーが却下判断を覆せるように、理由まで書く。

**収束を宣言するときは、その判定がどのスコープでのものかを書く**。ラウンド 2 以降は修正箇所を
中心に見ているので、「差分全体が clean」ではなく「ラウンド 1 で全体を見たうえで、以降の修正箇所を
追検証した結果」であることを明示する。

## やらないこと

- **push はしない**。コミットまでが責務。push して PR を更新するかはユーザーが決める
  （`/commit-push` か `git push` を案内する）。
- **検証が通っていない修正をコミットしない**（§1-5）。
- minor / nit を 0 にすること。好みの範囲の指摘で差分を膨らませない。
