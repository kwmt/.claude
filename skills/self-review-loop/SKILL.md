# self-review-loop — 重大な指摘が 0 になるまで回す

[self-review](../self-review/SKILL.md) を**修正込みのループに載せた版**。
「指摘を出す」で終わらず、**指摘の真偽を判定 → 直す → 検証 → 再レビュー**を、
対象 severity の指摘が 0 になるか、打ち切り条件に当たるまで繰り返す。

> **self-review との使い分け**: 指摘の一覧が欲しいだけなら `/self-review`。
> 人手レビューに出せる状態まで持っていきたいならこちら。
>
> **委譲ポリシー**: `disable-model-invocation: true` でユーザーの明示呼び出し専用。
> グローバル CLAUDE.md がサブエージェントによる自己検証を禁じている件は、
> self-review と同じ理由（ユーザーが明示的に要求した場合の例外）で成立する。自発起動しない。

## このスキルが失敗する典型的な形

先に書いておく。**ゴールを「指摘 0」に置くと、目的が「良いコードにする」から
「レビューアを黙らせる」にすり替わる**。具体的には:

- 誤検知を潰すために、本質的でない書き換えを入れてしまう
- 指摘が出た箇所ごとコードを消す・抽象化を剥がすなど、指摘を回避するだけの変更をする
- ラウンドを重ねるうちに、当初の依頼と関係ない改善でスコープが膨らむ
- 修正が新しい指摘を生み、それを直すとまた別の指摘が出る（振動）

だから**カウントすべきは「残った指摘の数」ではなく「未処理の指摘の数」**。
誤検知や意図的な設計判断は、直さずに **dismiss（理由付きで却下）** して 0 に数える。
これが成立するために、§3 の却下理由の記録が要る。

## 0. 開始前の確認

1. **現在の変更をコミット済みにする**。このスキルはコードを書き換えるので、
   元の変更と修正が未コミットで混ざると「何が元の実装で何がレビュー起因の修正か」が
   区別できなくなる。未コミットの変更があればユーザーに知らせ、先にコミットするか確認する。
2. **引数を解釈する**:
   - `--until=blocker` → blocker のみ 0 にする（速いが甘い）
   - `--until=major`（既定） → blocker と major を 0 にする
   - minor / nit は**ループの停止条件に含めない**。ここまで追うと収束しないし、
     好みの範囲の指摘で差分が膨らむ。最後に一覧として報告するに留める。
   - `--max-rounds=N`（既定 3）
3. **ベースを記録する**: ループ開始時点の HEAD を控えておく（報告時に「レビュー起因の修正」
   だけを差分として示すため）。

## 1. ラウンドの回し方

各ラウンドは レビュー → 判定 → 修正 → 検証 の 4 段。

### 1-1. レビュー

[self-review](../self-review/SKILL.md) の §0〜§2 をそのまま実行し、
重複排除・信頼度フィルタを通した**確定指摘**を得る。

**2 ラウンド目以降は観点と対象を絞る**（毎回 6 観点フル回転はコストの無駄）:

- **対象ファイル**: 前ラウンドの修正で触ったファイル + その修正が影響しうる呼び出し元
- **観点**: 前ラウンドで指摘が出た観点 + 🔒 セキュリティ + ✨ 正しさ / コード品質
  （後の 2 つは常に含める。修正がデグレを生む主経路がここだから）
- **既に判断済みの事項を渡す**: §3 で dismiss した指摘の一覧（file:line と却下理由）を
  各 subagent のプロンプトに入れ、「これらは判断済み。同じ指摘を再提出しない。ただし
  **却下理由が誤っていると考える根拠が新たにある場合は、その根拠を添えて再提出してよい**」
  と伝える。黙って握り潰すのではなく、反論の余地は残す。

### 1-2. 判定 — 直すか、却下するか

確定指摘を 1 件ずつ、**直す前に**次のどれかに分類する。ここを飛ばして片端から直すと、
誤検知への対応でコードが壊れる。

| 分類 | 条件 | 扱い |
|---|---|---|
| **fix** | 実際に問題で、この変更の責任範囲にある | 直す |
| **dismiss: 誤検知** | 該当ファイルを Read して確認した結果、問題ではない | 直さない。**何を確認して問題でないと判断したか**を記録 |
| **dismiss: 意図的** | ユーザーの指示・既存の設計判断として、そうなっているのが正しい | 直さない。**どの指示 / 判断に基づくか**を記録 |
| **defer: 範囲外** | 実際に問題だが、今回の変更が持ち込んだものではない（既存の課題） | 直さない。報告に「既存の課題」として分離して載せる |

判断がつかない blocker は、**ユーザーに聞く**。勝手に dismiss しない。

`defer` を認めているのは、スコープ逸脱を防ぐため。既存コードの問題まで直し始めると
差分が肥大して、本来レビューされるべき変更が埋もれる。

### 1-3. 修正

- fix に分類した指摘だけを直す。
- **指摘の file:line だけを見て機械的に直さない**。なぜその指摘が出たかを理解してから直す。
  同じ原因が他の箇所にもあるなら、そこも直す（ただし §1-2 の defer 基準は守る）。
- 修正はメインループが自分で行う。**修正のためにサブエージェントを起動しない**
  （並列で同じワーキングツリーを書き換えると競合するし、修正には会話の文脈が要る）。

### 1-4. 検証

**指摘が消えたことを再レビューで確認する前に、コードが動くことを実際に確認する。**
レビューは静的な読みなので、修正がビルドを壊していても指摘は減る。

- プロジェクトのテスト / lint / 型チェック / ビルドを**実際に走らせる**
  （コマンドは README・CI 設定・`package.json` の scripts 等から見つける）
- 見つからなければ、その旨を報告に書く（「検証コマンドが特定できなかった」）
- 失敗したら、次のラウンドに進む前にここで直す

## 2. 打ち切り条件

次のいずれかに当たったら**ループを止めてユーザーに報告する**。粘っても良くならない。

1. **収束**: 対象 severity の未処理指摘が 0 になった（成功）
2. `--max-rounds` に到達した
3. **同じ指摘が 2 ラウンド連続で出る**: 修正が効いていない。アプローチが間違っている可能性が高い
4. **振動**: 修正が、同 severity の新しい指摘を生むのが 2 回続いた。
   設計レベルの問題を局所修正で潰そうとしているサイン
5. **判断がつかない blocker が残った**: ユーザーに聞くべきものが残っている
6. **差分が当初の 2 倍を超えた**: スコープが膨らんでいる。一度止めて方針を確認する

2〜6 は失敗ではなく**中断**。そこまでに直したものと、残っているものを正直に報告する。

## 3. 報告

ループが終わったら、次を報告する。ラウンドごとの実況は要らない（結果だけでよい）。

```
## 結果
<収束した / 打ち切った（理由）>  ラウンド数: N

## 直したもの
- <file:line> <severity> <指摘の要旨> → <どう直したか>

## 却下したもの
- <file:line> <severity> <指摘の要旨> → <却下の分類と理由>

## 既存の課題として残したもの（defer）
- <file:line> <severity> <指摘の要旨>

## 残っている指摘
- <blocker/major が残っているなら、なぜ残ったか>
- <minor / nit の一覧。停止条件には含めていない旨を添える>

## 検証
- <実行したコマンドと結果。特定できなかった場合はその旨>

## レビュー起因の差分
- <ループ開始時点の HEAD からの差分の統計>
```

- **却下したものを必ず載せる**。ここが隠れると「指摘 0」が信用できなくなる。
  ユーザーが却下判断を覆せるように、理由まで書く。
- 各 subagent の生ログは貼らない。

## やらないこと

- **コミット・push はしない**。修正を適用するところまでが責務。
  コミットするかはユーザーが決める（`/commit` を案内する）。
- minor / nit を 0 にすること。好みの範囲の指摘で差分を膨らませない。
- 指摘を消すためだけの変更。§冒頭で書いたとおり、これが一番やってはいけないこと。
