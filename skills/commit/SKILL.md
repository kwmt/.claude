# git commit スキル

## 哲学

- **小さく意味のある単位でコミットする**。1 コミット = 1 つの意図。レビューしやすく、
  デグレしたときに revert / bisect で追える。
- **何をしたかと同じくらい、なぜそうしたかを残す**。差分を読めば「何を」は分かるが、
  「なぜ」は書かないと失われる。会話で得た理由・背景をそのまま本文に落とす。
- **面倒な部分は Claude が担う**。件名の考案・理由の言語化・分割案の提示はこちらの仕事。
  ユーザーに判断させるのは、意図が複数に割れていて分け方が一意に決まらないときだけ。

## コミットメッセージの書式

```
<emoji> 件名（何をしたか・体言止め）

なぜそうしたか。会話で得た文脈・制約・却下した代案をそのまま書く。
```

- **gitmoji を使う**。絵文字そのもの（✨）を書く。テキスト表現（`:sparkles:`）は使わない。
- 件名は 1 行・簡潔に。理由が自明な変更なら本文は省略して 1 行で良い。
- 本文は「なぜ」に使う。差分を読めば分かる「何を」の再説明で埋めない。
- 言語は**そのリポジトリの既存履歴に合わせる**（`git log --oneline -20` で確認）。
- issue / PR 番号が分かっているなら件名末尾に添える（例: `(#458)`）。

## 実行フロー

1. `git status` と `git diff`（staged があれば `git diff --staged` も）で変更全体を把握する。
2. **`git add .` を使わない**。ファイル単位で staging する。1 ファイル内に別意図が混ざるなら
   ハンク単位で分ける。
3. 変更が複数の意図にまたがるなら**コミットを分ける**。生成物（コード生成・golden 画像等）や
   バイナリは、それを生んだ手書きの変更と別コミットにする（レビュー時に差分が埋もれない）。
4. `git commit -m` で実行する（本文を持つ場合はヒアドキュメントで渡す）。
5. `git log --oneline -5` で結果を確認して報告する。

## 直前コミットへの吸収

「直前のコミットの続き・書き忘れ」に見える変更は、新しいコミットを作らず `--amend` で吸収する。
**push 前に限る**。push 済みのコミットは amend / rebase しない（他人の履歴を壊す）。

## ユーザーに確認するタイミング

以下だけは勝手に決めずに聞く。それ以外は判断して進める。

- 変更に複数の意図が混在し、分け方が一意に決まらないとき（分割案を提示して選んでもらう）
- 直前コミットへ吸収すべきか、独立コミットにすべきか判断が割れるとき
- 意図せず入ったように見える変更（デバッグコード・ローカル用ポート・鍵らしき文字列・
  大きな生成物）が含まれるとき。**コミットに含める前に指摘する**

## 守ること

- **秘匿情報をコミットしない**。`.env`・鍵・トークン・`*.jks` 等が差分にあれば止めて報告する。
- **ローカル用の一時変更をコミットしない**（接続先ポートの書き換え・一時的な skip 等）。
- リポジトリに規約（`CLAUDE.md` / `.claude/rules/` / `CONTRIBUTING.md`）があればそれを優先する。
  ブランチ運用の制約（保護ブランチで直接作業しない等）もそこに従う。
- push を求められた場合のみ push する。求められていないのに push・PR 作成をしない。
