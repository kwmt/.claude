# pr-review-followup — 付いたレビュー指摘に決着をつける

外から来た指摘を**収集 → 真偽判定 → 対応 → 返信**まで運ぶ。
`self-review` が「指摘を作る」側なのに対し、こちらは**他人（bot 含む）が作った指摘を受ける**側。

対象は Claude Code Review の bot に限らない。人間のレビュワーのコメントも同じ流れで扱える。

> **委譲しない**。指摘はすでに外部のレビュワーが作っており、それが正しいかを確かめるのは
> 自分の仕事。ここで subagent を立てると、CLAUDE.md が禁じている「自分の作業の検証の委譲」に
> そのまま当たる。差分が大きくて**新たに**多観点レビューが要るなら、それは `/self-review` の仕事。

## 0. レビューを集める

### 0-1. 取得

```bash
~/.claude/skills/pr-review-followup/scripts/fetch-pr-review.sh [PR番号]
```

PR 番号を省略すると現在のブランチの PR を見る。別リポジトリなら `--repo OWNER/NAME`。
JSON をファイルに落として**索引だけ**を出す。レビュー本文は数万字になるので、
索引を見てから必要な節だけ `python3` / `jq` で読む。JSON のパスは索引の `json:` 行にある。

レビューは 3 か所に分かれて存在する。**どれか 1 つを見て終わりにしない**。

| 場所 | JSON のパス | 中身 |
|------|------------|------|
| 総括コメント | `comments.nodes[]` | bot の「PR #N レビュー」本体。ここに指摘の大半がある |
| レビュー本体 | `reviews.nodes[]` | `APPROVED` / `CHANGES_REQUESTED` と、その本文 |
| インラインスレッド | `reviewThreads.nodes[]` | 行に紐づく指摘。`isResolved` と `thread_id` を持つ |

### 0-2. 上書きで消えた指摘を拾う

**ここが一番取りこぼしやすい。** Claude Code Review の bot は PR ごとに
**1 件のコメントを毎回上書き更新する**。再 push すると、前回の指摘本文は
「レビュー中…」のチェックリストに置き換わって画面から消える。
`updated_at != created_at` のコメントで、いま見えている本文が
進捗チェックリストだけなら、**指摘は編集履歴の中にある**。

索引の `編集履歴=N件` と各 `edits[i]` の字数を見る。字数が大きい版が実体のあるレビュー。

```bash
python3 -c "
import json
d=json.load(open('<json のパス>'))
c=d['data']['repository']['pullRequest']['comments']['nodes'][0]
print(c['userContentEdits']['nodes'][6]['diff'])   # 索引で当たりを付けた世代
"
```

古い版を読むときは**それがどの commit に対するレビューか**を必ず意識する。
`editedAt` より後に push があれば、その指摘はすでに直っているかもしれないし、
指摘された行自体が消えているかもしれない。索引の `head:` 行の `committedDate` と見比べる。

### 0-3. レビューが無い・走っていない場合

- 索引が「レビューは 1 件も付いていない」→ まだレビューが走っていない。
  待つか、ワークフローを再実行するようユーザーに伝える。勝手に何かを直し始めない。
- `github-actions[bot]` の `<!-- claude-review-usage-limit -->` コメントがある
  → **利用上限でレビューがスキップされた**。コードの問題ではない。
  「上限リセット後に再 push かジョブ再実行でレビューされる」と伝えて終わる。
- bot のコメントがチェックリストだけで `[ ]` が残っている → **レビュー実行中**。
  途中の状態に対応しても無駄になる。終わるまで待つ。

### 0-4. すでに対応済みのものを除く

再実行しても同じ返信を二重に投稿しないために、ここで必ず絞る。

- `isResolved: true` のスレッドは対応済み。触らない。
- 自分（`gh api user -q .login`）の返信がスレッドの末尾にあり、その後に bot の追記が無ければ対応済み。
- 総括コメントに対する自分の返信コメントが、その指摘世代の `editedAt` より後にあれば対応済み。
  ただし**その後さらに新しいレビュー世代が来ていればそれは未対応**。

## 1. 指摘を仕分ける

Claude のレビューは**指摘と確認と賛辞が同じ見出しレベルで混ざる**。
`✅` は「見て問題なかった」の報告であって指摘ではない。これを指摘として数えると、
直すところが無いのに何かをいじる羽目になる。実際のレビューに出る形:

| 見出し | 意味 | 対応 |
|--------|------|------|
| `✅ …は正しい` / `総括: LGTM` | 確認済みの報告 | 対応不要。返信でも触れない |
| `🔍 確認: …` | レビュワーが確信を持てず投げた質問 | **答える**。直す必要は無いことが多い |
| `💬 軽微:` / `軽微な所感（ブロック不要）` | 直さなくてよいと自称している指摘 | 判断して答える。直すなら直す |
| 指摘・`指摘事項:` | 直すことを期待されている | 真偽を確かめる |

そのうえで**一件ずつ、実際にコードを読んで**次のどれかに決める。
レビュー文の主張をそのまま信じない。bot は差分だけを見て周辺を読めていないことがあり、
「バグだ」と書かれていても実際には別の場所で守られていることがある。

- **真** — 直す
- **偽（誤検知）** — 直さない。なぜ成り立たないかを、コードの場所を挙げて言えること
- **真だが直さない** — 意図的にそうしている。**なぜそう決めたかを答える**
- **真だが今回の範囲外** — pre-existing の問題など。別 issue にするか、そう伝える

`--dry-run` ならここまでで止め、仕分け結果を表にして報告する。

### 「直さない」を選ぶことを恐れない

このスキルが一番失敗する形は、**指摘を黙らせるために本質的でない書き換えを入れること**。
ゴールは「指摘を消すこと」ではなく「コードを正しくすること」。

判断の基準は、レビュワーが挙げた懸念が**実際に起きうるか**。起きないなら直さない。
実際、過去には「GA4 の上限 40 文字に揃えるべきでは」という指摘に対して
「ここは分類のための判定であって送信名の検査ではないので、意図的に 64 で緩めている」と
答えるのが正解だった。直していたら長い名前のイベントが静かに合流していた。

## 2. 直して、確かめる

- 直すのは**指摘された事象そのもの**。ついでのリファクタでスコープを膨らませない。
- 直したら**それが直ったことを示すテスト**を足す。指摘が「将来こうなると壊れる」型なら、
  その将来の入力でテストを書く。テストが書けないなら、なぜ書けないかを返信に書く。
- 直す過程で見つけた同種の問題は直してよい。返信で「指摘の 2 箇所に加えてこれも直した」と言う。
- プロジェクトのテスト・lint を実行して通す。落ちたら落ちたと報告する。
- コミットは `commit` スキルに従う。**指摘ごとに 1 コミット**が追いやすい。

## 3. PR に返信する

直しただけでレビュワーに何も返さないと、指摘が通じたのか無視されたのか分からない。
**インライン指摘にはスレッドで、総括指摘にはコメント 1 本で**返す。

### インラインスレッドへの返信と解決

```bash
# 返信（<comment_id> はスレッド先頭コメントの databaseId）
gh api repos/{owner}/{repo}/pulls/<PR>/comments/<comment_id>/replies -f body="$(cat reply.md)"

# 解決（<thread_id> は索引の thread_id=PRRT_... をそのまま使う）
gh api graphql -f query='mutation($id:ID!){resolveReviewThread(input:{threadId:$id}){thread{isResolved}}}' -f id=<thread_id>
```

解決するのは**対応が終わったスレッドだけ**。直さないと決めたものも、
理由を返信したうえで解決してよい。返信せずに解決するのは、指摘を握り潰すのと同じ。

### 総括コメントへの返信

```bash
gh pr comment <PR> --body-file <ファイル>
```

`--body-file` を使う。body を渡さないと `gh` が対話プロンプトで入力を待って止まる。

書式は「何をどう扱ったか」が指摘ごとに分かること。既存の書き方に揃える:

```markdown
レビュー指摘を反映しました。

- **<指摘の要点>**: <どうしたか。直したなら理由も。直さないなら、なぜ成り立たないか>
- **<指摘の要点>**: ご指摘のとおり…／ご質問の件、<根拠>のため意図的にこうしています

## 追加: <指摘をきっかけに自分で見つけて直したもの>
<あれば>
```

- **反論するときほど根拠を具体的に**書く。ファイル名・行・実測値・仕様の出典。
  「問題ありません」だけでは、レビュワーは確かめようがない。
- 自分で入れてしまったバグに気づいたら、それも書く。隠すと次のレビューで見つかる。
- 直していないのに「反映しました」と書かない。**実際にやったことだけ**を書く。

## この作業が失敗する典型的な形

- **上書きされた指摘を見落とす**。画面に「レビュー中…」しか無いのを見て「指摘なし」と結論する。
  §0-2 を飛ばさない。
- **`✅` を指摘として数える**。直すところが無いのに何かをいじる。
- **レビュー文を検証せずに直す**。bot の誤検知に合わせてコードを歪める。
- **返信だけして直さない / 直して返信しない**。どちらも片手落ち。
- **古い世代の指摘に対応する**。すでに直っている箇所を「直しました」と報告してしまう。
  `editedAt` と head commit の時刻を必ず見比べる。
- **二重投稿**。再実行時に §0-4 の除外をせず、同じ返信をもう一度貼る。
