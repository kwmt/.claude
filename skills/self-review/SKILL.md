# self-review — 多観点の並列セルフレビュー

`$ARGUMENTS` を入力に、変更を観点ごとに subagent で並列レビューし、
指摘を集約 → 重複排除 → **信頼度が一定以上のものだけ**に絞って報告する。

> **`/code-review` との使い分け**: 組み込みの `/code-review` は単発（または `ultra` でクラウド並列）。
> こちらは観点を明示的に並列分業する。
>
> **委譲ポリシー**: CLAUDE.md は「自分の作業の検証・ダブルチェックを目的としたサブエージェント」を
> 無条件に禁じている。この skill が抵触しない根拠は「ユーザーが呼んだから例外」ではなく、
> CLAUDE.md が委譲を認める役割として**レビュワー（差分が大きい、またはセキュリティ・
> パフォーマンス上のリスクが高いとき）**を挙げている点にある。§0-3 の規模テーブルは、
> その条件を満たすときだけ委譲するための実装。条件を満たさない小さな差分では委譲しない。

## 0. レビュー対象と観点の確定

### 0-1. 差分スコープを決める

以下で得る **`<base>`（`origin/` を含まない生のブランチ名）** に統一する。
`origin/` を二重に付けると `origin/origin/main` になって落ちるので、必ずここで正規化する。

1. `$ARGUMENTS` に **PR 番号**があれば対象はその PR:
   - `gh pr view <PR> --json title,body,baseRefName,headRefName,headRefOid,additions,deletions,changedFiles`
   - 差分は `gh pr diff <PR>`。**これがレビュースコープで、ローカルの未コミット差分は対象外**。
   - 同じブランチをチェックアウト済みなら周辺コードは Read でよい。違うブランチにいるなら
     `gh api "repos/{owner}/{repo}/contents/<path>?ref=<headRefOid>" -q .content | base64 -d`
     （`{owner}/{repo}` はそのまま書ける。レスポンスは base64 なので必ずデコードする）。
2. PR 番号が無ければ対象は**現在のブランチ差分**。`<base>` はこの順で決める:
   - `gh pr view --json number,baseRefName`。**PR が無いと非ゼロ終了するが、これは正常系**
     （「PR がまだ無い」だけ）。エラーで止まらず次に進む。
   - `git symbolic-ref --short refs/remotes/origin/HEAD | sed 's#^origin/##'`。
     `--short` は `refs/remotes/` までしか剥がさず `origin/main` を返すので、`sed` が要る。
   - それも無ければ `main` / `develop` / `staging` のうち origin に存在するものから推定し、
     どれを使ったかを報告に明記する。
   - `gh` が未認証、またはリモートが GitHub でないなら、PR 系の手順は全て飛ばして git だけで決める。
   - 決まったら `git fetch origin <base>` の後 `git diff origin/<base>...HEAD`
     （三点。マージコミット由来のノイズを避ける）。
3. **差分が空になる状況を先に潰す**。次に当たったら、そのままレビューせずユーザーに確認する:
   - 現在いるのが `<base>` そのもの
   - detached HEAD、または upstream 未設定のローカル専用ブランチ
     （`origin/HEAD` 由来のベースと比べて意図しない巨大差分になりやすい）

### 0-2. プロジェクト固有の判断材料を集める

グローバルスキルなので、規約はハードコードせず**その場のリポジトリから読む**。
subagent に「何を根拠に規約違反と判断するか」を渡さないと、一般論しか返ってこない。

- `CLAUDE.md` — **グローバル（`~/.claude/CLAUDE.md`）とプロジェクト（リポジトリ直下）の両方が
  ありうる。両方読み、どちらの規約かを subagent に明示する**。混同すると「その規約は存在しない」
  という誤検知が出る。`.claude/rules/*.md` / `.cursorrules` / `CONTRIBUTING.md` も同様に拾う
- lint / formatter 設定（`.eslintrc*`, `analysis_options.yaml`, `clippy.toml`, `ruff.toml` 等）
- 変更ファイルの**隣接する既存コード** — 明文化されていない慣習はここにしかない
- PR 本文 / 紐づく issue（`gh issue view`）/ この会話で与えられた要求 — 要件検証の根拠

見つかったものだけを根拠として渡す。無い項目は「根拠なし」として観点ごと落として構わない
（存在しない規約をでっち上げさせない）。**未コミットの規約変更が作業ツリーにあることもある**ので、
`git status` が汚れているなら on-disk の内容を正としてよいか一度確認する。

### 0-3. 委譲するかどうか、何観点にするかを決める

CLAUDE.md は「1体で足りるなら1体にし、起動数は低く保つ」と定めている。
差分に対して過剰な並列は、コストが増えるだけで指摘は増えない。

| 差分規模 | 進め方 |
|---|---|
| 1〜2 ファイル・数十行 | **委譲しない**。メインループが §1 の観点表を頭に置いて自分で読む |
| 中規模（〜10 ファイル程度） | 観点を 3 つに束ねて起動（セキュリティ+品質 / 規約+simplify / 要件+チェックリスト） |
| PR 相当（〜30 ファイル） | 下表の 6 観点をそれぞれ並列起動 |
| それ以上 | 全観点を一度に回さない。対象ファイルを分割するか観点を間引く方針をユーザーに相談する |

## 1. 観点ごとに subagent を並列起動

**§0-3 で委譲すると決めた場合のみ**この節に進む。
**1 つの応答内で Agent ツール呼び出しをまとめて発行し、並列実行させる**（逐次に投げない）。

各 subagent には (a) レビュー対象の取得方法、(b) 観点の focus、(c) §0-2 で集めた根拠の**具体的な
ファイルパス**、(d) 後述の出力フォーマットと共通の但し書き、を渡す。

| # | 観点 | focus |
|---|---|---|
| 1 | 🔒 セキュリティ | 秘匿値・認証情報・PII の取り扱い（ログ / 解析イベント / エラーメッセージへの混入）・入力検証・インジェクション・権限チェック漏れ・安全でない既定値・依存追加の素性 |
| 2 | ✨ 正しさ / コード品質 | ロジックの誤り・エッジケース（空 / 境界 / 同時実行）・エラーと例外の扱い・非同期の競合とリーク・null / Option の扱い・破壊的変更の影響範囲 |
| 3 | 📐 規約準拠 | §0-2 で見つけた規約・lint 設定・**隣接コードの慣習**との整合。レイヤー構造 / 依存方向・命名・ファイル配置。根拠が示せない「好み」は nit として返す |
| 4 | 🧹 simplify | 既存の関数 / コンポーネントで足りないか（再利用）・重複の共通化・過剰な抽象と早すぎる一般化・altitude（呼び出し側で書くべき分岐が下層に漏れていないか）・デッドコード |
| 5 | 🎯 要件検証 | 変更が対応する要件（PR 本文 / issue / 会話の指示）に**合致**しているか。受け入れ条件の取りこぼし・要求外の実装（スコープ逸脱）・仕様の誤読 |
| 6 | ☑️ 同 PR 完結チェック | この PR 内で揃っているべき随伴物: 変更ロジックに対応するテスト・生成物やスナップショットの再生成・設定 / マイグレーション / ドキュメントの追随・多言語文言の全ロケール追加・feature flag の後始末 |

**エージェント型**: 観点 2 は技術スタックに合わせる（React → `react-frontend-specialist`、
iOS / Android の UI → `ios-ux-reviewer` / `android-ux-reviewer`、その他 →
`code-review-specialist`）。観点 1 は Rust なら `rust-security-specialist`。
それ以外は全て `general-purpose` でよい。コストを抑えたいときは `model: sonnet` を渡す
（レビュー精度は落ちにくい）。

### subagent に渡す出力フォーマット

この形で列挙して返させる（人向けの整形はさせない。整形はメインループの仕事）:

```
- file: <repo 相対パス>
  line: <1-indexed。範囲なら開始行>
  perspective: <security|quality|convention|simplify|requirements|checklist>
  severity: <blocker|major|minor|nit>
  confidence: <high|medium|low>   # 実際に問題である確からしさ。憶測は low
  summary: <一文>
  detail: <なぜ問題か。可能なら「この入力 → この誤動作」の具体シナリオ>
  fix: <推奨する具体的な修正>
```

各プロンプトに入れる共通の但し書き:

- **気づいた問題は全件返す**。「重大なものだけ」「保守的に」と subagent 側で絞らせない
  （指示どおり報告数を減らしてしまう）。取捨選択は §2 のメインループが行う。
- 指摘は必ず対象 diff の具体箇所（file:line）に紐づける。一般論・好みの範囲に留まる指摘は、
  そうと分かるよう `severity: nit` / `confidence: low` を付けて返す（黙って捨てない）。
- 指摘の前に周辺コードを Read で確認する（既に別レイヤーで担保されていないか、既存の同種実装は
  どうなっているか）。確認した結果の確からしさを `confidence` に正直に反映する。
- **`file` は必ず repo 相対パスで書く。`detail` / `fix` にローカル絶対パス
  （`/Users/...` 等）・秘匿値やトークンの実値・実在する PII を書かない**
  （プレースホルダにする）。§3 でそのまま公開 PR に転記されうる。
- **読み取り専用**。コードは書き換えず、指摘と fix 案だけ返す。
- 長くなる場合は返信本文ではなくファイルに書き出させる（返信は途中で切り詰められる）。

## 2. 集約・重複排除・信頼度フィルタ（メインループで行う）

subagent の結果が揃ったら統合する。ここを飛ばして生の指摘を並べると、誤検知と重複でノイズになる。

1. **重複排除**: `(file, line, summary)` が実質同じ指摘は 1 件に統合する。複数観点が同じ箇所を
   指しているなら perspective を併記して 1 件にまとめる。
2. **信頼度フィルタ**: `confidence: low` は落とす。**ただし `severity: blocker` は confidence を
   問わず残し、3 の追検証にかける**（取りこぼすと一番痛いものを、フィルタで黙って消さない）。
3. **追検証**: blocker / major で確信が持てないものは、**メインループ自身が該当ファイルを Read
   して真偽を確認**してから残す / 落とす。subagent の誤検知をここで濾す。
   **subagent が読んだ前提が古い可能性も疑う**（未コミットの変更、別ブランチの内容など）。
4. **ランク付け**: severity（blocker > major > minor > nit）→ confidence の順に並べる。

## 3. 報告

- 残った指摘を **severity 降順**で一覧報告する。各指摘に file:line・観点・severity・confidence・
  要旨・推奨修正を付ける。
- **0 件なら「確度の高い指摘なし」と明言する**。無理に絞り出さない。
- 併せて**観点ごとのカバレッジ**を 1 行ずつ添える（各観点が何を見て、指摘があったか / 無かったか）。
  巨大差分で割愛した箇所など「見ていない / 見られなかった」ものがあれば正直に書く。
- 各 subagent の生ログ・中間出力はユーザーに貼らない。結論だけを引用する。

### `--comment` — PR へのインライン投稿

**投稿先**: `$ARGUMENTS` の PR 番号。省略されていても §0-1 の 2 で現在のブランチの PR が
見つかっていればそれを使う。どちらも無ければ投稿せず、その旨を伝えて通常報告にフォールバックする。

投稿は取り消しづらい書き込み操作なので、**先に投稿予定の全文をユーザーに提示して承認を取る**。
承認前に投稿しない。

- 対象は §2 を通過した確定指摘のみ。**観点 1（セキュリティ）の指摘は既定でインライン投稿から
  外す**（秘匿値や PII の実値が本文に入りやすく、公開リポジトリでは恒久的な公開記録になる）。
  投稿するなら値をプレースホルダに置き換えてから。絶対パスも同様に落とす。
- インラインコメントは `line` + `side` を使う（`position` は deprecated で、ずれの温床）:
  ```
  gh api repos/{owner}/{repo}/pulls/<PR>/comments \
    -f body='...' \
    -f commit_id="$(gh pr view <PR> --json headRefOid -q .headRefOid)" \
    -f path='<repo 相対パス>' -F line=<n> -f side=RIGHT
  ```
  `gh api` はパラメータを付けると自動で POST になる（付けないと GET ＝既存コメントの一覧取得に
  なるので、「投稿した」と誤認しないこと）。`commit_id` は PR head の最新 SHA を使う。
- **diff に含まれない行を指す指摘は、最初からインライン化しない**（422 になる）。
  それらは 1 件のまとめコメントに回す: `gh pr comment <PR> --body-file <tmp>`。
  `--body` / `--body-file` を渡さないと対話プロンプトで停止する。
  まとめコメントに入れるのは**インライン投稿しなかった分だけ**（二重掲載を避ける）。
- AI が GitHub に書くコメントは、本文末尾に必ず次の 1 行を付ける（CLAUDE.md のグローバル規約）:
  `— 🤖 この返信は AI が作成しました`

## やらないこと

- **修正はこの skill では行わない**。自己点検が目的で、指摘の採否と修正はユーザーが決める。
  指摘を直すところまで自動で回したいなら `~/.claude/skills/self-review-loop/SKILL.md` を案内する。
  単発で直すだけなら `/code-review --fix` や手作業でよい。
- コスト意識: 6 並列 subagent は相応にトークンを使う。§0-3 の規模判定を飛ばさない。
