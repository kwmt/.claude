# self-review — 多観点の並列セルフレビュー

`$ARGUMENTS` を入力に、変更を**観点ごとに subagent を並列に走らせて**レビューし、
指摘を集約 → 重複排除 → **信頼度が一定以上のものだけ**に絞って報告する。

> **位置づけ**: 組み込みの `/code-review`（単発・または `ultra` でクラウド並列）とは別に、
> **観点を明示的に並列分業**するセルフレビュー。人手レビューに出す前の自己点検に使う。
>
> **委譲ポリシーとの関係**: グローバル CLAUDE.md は「自分の作業の検証目的でサブエージェントを
> 使う」ことを禁じている。この skill は `disable-model-invocation: true` で**ユーザーが明示的に
> 呼んだときだけ**動く＝「ユーザーが明示的にチームを要求した場合」に当たるため例外に該当する。
> 自発的に起動してはいけない。

## 0. レビュー対象と観点の確定

### 0-1. 差分スコープを決める

1. `$ARGUMENTS` に **PR 番号**があれば対象はその PR:
   - `gh pr view <PR> --json title,body,baseRefName,headRefName,additions,deletions,changedFiles`
   - 差分は `gh pr diff <PR>`。**これがレビュースコープで、ローカルの未コミット差分は対象外**。
     同じブランチをチェックアウト済みなら周辺コードは Read してよい。違うブランチにいるなら
     `gh api` でファイルを取得する。
2. PR 番号が無ければ対象は**現在のブランチ差分**。ベースブランチはこの順で決める:
   - `gh pr view --json number,baseRefName`（現在のブランチに PR があればその base が正）
   - 無ければ `git symbolic-ref --short refs/remotes/origin/HEAD` でデフォルトブランチ
   - それも無ければ `main` / `develop` / `staging` のうち origin に存在するものから推定し、
     どれを使ったかを報告に明記する
   - `git fetch origin <base>` してから `git diff origin/<base>...HEAD`
     （三点。マージコミット由来のノイズを避ける）
3. 現在いるのがベースブランチそのものなら差分は空になる。その旨を伝えて機能ブランチでの実行を促す。
4. 差分が空／巨大すぎるときはユーザーに確認する（巨大なら観点ごとに担当ファイル群を分割して渡す）。

### 0-2. プロジェクト固有の判断材料を集める

グローバルスキルなので、規約はハードコードせず**その場のリポジトリから読む**。
subagent に「何を根拠に規約違反と判断するか」を渡さないと、一般論しか返ってこない。

- `CLAUDE.md` / `.claude/rules/*.md` / `.cursorrules` / `CONTRIBUTING.md` — 明文化された規約
- lint / formatter 設定（`.eslintrc*`, `analysis_options.yaml`, `clippy.toml`, `ruff.toml` 等）
- 変更ファイルの**隣接する既存コード** — 明文化されていない慣習はここにしかない
- PR 本文 / 紐づく issue（`gh issue view`）/ この会話で与えられた要求 — 要件検証の根拠

見つかったものだけを根拠として渡す。無い項目は「根拠なし」として観点ごと落として構わない
（存在しない規約をでっち上げさせない）。

### 0-3. 観点数を差分規模に合わせる

スポーン数は最小に保つ。差分に対して過剰な並列は、コストが増えるだけで指摘は増えない。

| 差分規模 | 進め方 |
|---|---|
| 1〜2 ファイル・数十行 | **委譲しない**。メインループが自分で §1 の観点表を頭に置いて読む |
| 中規模（〜10 ファイル程度） | 観点を 3 つ程度に束ねて起動（例: セキュリティ+品質 / 規約+simplify / 要件+チェックリスト） |
| PR 相当以上 | 下表の 6 観点をそれぞれ並列起動 |

## 1. 観点ごとに subagent を並列起動

**1 つの応答内で Agent ツール呼び出しをまとめて発行し、並列実行させる**（逐次に投げない）。
**effort は `medium`**（レビュー精度は低い effort でも保たれる。既定の high 任せにしない）。

各 subagent には (a) レビュー対象の取得方法、(b) 観点の focus、(c) §0-2 で集めた根拠の**具体的な
ファイルパス**、(d) 後述の出力フォーマット、(e) 「気づいた問題は severity / confidence を付けて
**全件**返す（絞り込みはメインループが行う）」を渡す。

| # | 観点 | focus |
|---|---|---|
| 1 | 🔒 セキュリティ | 秘匿値・認証情報・PII の取り扱い（ログ / 解析イベント / エラーメッセージへの混入）・入力検証・インジェクション・権限チェック漏れ・安全でない既定値・依存追加の素性 |
| 2 | ✨ 正しさ / コード品質 | ロジックの誤り・エッジケース（空 / 境界 / 同時実行）・エラーと例外の扱い・非同期の競合とリーク・null / Option の扱い・破壊的変更の影響範囲 |
| 3 | 📐 規約準拠 | §0-2 で見つけた規約・lint 設定・**隣接コードの慣習**との整合。レイヤー構造 / 依存方向・命名・ファイル配置。根拠が示せない「好み」は nit として返す |
| 4 | 🧹 simplify | 既存の関数 / コンポーネントで足りないか（再利用）・重複の共通化・過剰な抽象と早すぎる一般化・altitude（呼び出し側で書くべき分岐が下層に漏れていないか）・デッドコード |
| 5 | 🎯 要件検証 | 変更が対応する要件（PR 本文 / issue / 会話の指示）に**合致**しているか。受け入れ条件の取りこぼし・要求外の実装（スコープ逸脱）・仕様の誤読 |
| 6 | ☑️ 同 PR 完結チェック | この PR 内で揃っているべき随伴物: 変更ロジックに対応するテスト・生成物やスナップショットの再生成・設定 / マイグレーション / ドキュメントの追随・多言語文言の全ロケール追加・feature flag の後始末 |

### エージェント型の選び方

観点 1・2 は、変更対象の技術スタックに専門エージェントがあればそれを使う。
無ければ `general-purpose` にフォールバックする。

| 変更の中身 | 観点 1（セキュリティ） | 観点 2（品質） |
|---|---|---|
| Rust | `rust-security-specialist` | `code-review-specialist` |
| React / フロントエンド | `general-purpose` | `react-frontend-specialist` |
| iOS / Android の UI | `general-purpose` | `ios-ux-reviewer` / `android-ux-reviewer` |
| その他 | `general-purpose` | `code-review-specialist` |

観点 3〜6 は `general-purpose` でよい。

### subagent に渡す出力フォーマット

この形で列挙して返させる（人向けの整形はさせない。整形はメインループの仕事）:

```
- file: <repo 相対パス>
  line: <1-indexed。範囲なら開始行>
  perspective: <security|quality|convention|simplify|requirements|checklist>
  severity: <blocker|major|minor|nit>
  confidence: <high|medium|low>   # 実際に問題である確からしさ。憶測は low
  summary: <一文>
  detail: <なぜ問題か。可能なら「この入力 → この誤動作」の具体シナリオ>
  fix: <推奨する具体的な修正>
```

各プロンプトに入れる共通の但し書き:

- **気づいた問題は全件返す**。「重大なものだけ」「保守的に」と subagent 側で絞らせない
  （指示どおり報告数を減らしてしまう）。取捨選択は §2 のメインループが行う。
- 指摘は必ず対象 diff の具体箇所（file:line）に紐づける。一般論・好みの範囲に留まる指摘は、
  そうと分かるよう `severity: nit` / `confidence: low` を付けて返す（黙って捨てない）。
- 指摘の前に周辺コードを Read で確認する（既に別レイヤーで担保されていないか、既存の同種実装は
  どうなっているか）。確認した結果の確からしさを `confidence` に正直に反映する。
- **読み取り専用**。コードは書き換えず、指摘と fix 案だけ返す。

## 2. 集約・重複排除・信頼度フィルタ（メインループで行う）

subagent の結果が揃ったら統合する。ここを飛ばして生の指摘を並べると、誤検知と重複でノイズになる。

1. **重複排除**: `(file, line, summary)` が実質同じ指摘は 1 件に統合する。複数観点が同じ箇所を
   指しているなら perspective を併記して 1 件にまとめる。
2. **信頼度フィルタ**: `confidence: low` は落とす。ただし `severity: blocker` は `medium` でも
   残す（重大なものを取りこぼさない）。
3. **追検証**: blocker / major で確信が持てないものは、**メインループ自身が該当ファイルを Read
   して真偽を確認**してから残す / 落とす。subagent の誤検知をここで濾す。
4. **ランク付け**: severity（blocker > major > minor > nit）→ confidence の順に並べる。

## 3. 報告

- 残った指摘を **severity 降順**で一覧報告する。各指摘に file:line・観点・severity・confidence・
  要旨・推奨修正を付ける。
- **0 件なら「確度の高い指摘なし」と明言する**。無理に絞り出さない。
- 併せて**観点ごとのカバレッジ**を 1 行ずつ添える（各観点が何を見て、指摘があったか / 無かったか）。
  巨大差分で割愛した箇所など「見ていない / 見られなかった」ものがあれば正直に書く。
- 各 subagent の生ログ・中間出力はユーザーに貼らない。結論だけを引用する。

### `--comment` が指定され、対象が PR の場合

**§2 を通過した確定指摘のみ**を PR にインラインコメントとして投稿する。

- `gh api repos/<owner>/<repo>/pulls/<PR>/comments` を使う。position がずれる場合は
  まとめて 1 件の PR コメント（`gh pr comment`）にフォールバックする。
- AI が GitHub に書くコメントは、本文末尾に必ず次の 1 行を付ける（グローバル規約）:
  `— 🤖 この返信は AI が作成しました`

## やらないこと

- **修正はこの skill では行わない**。自己点検が目的で、指摘の採否と修正はユーザーが決める。
  指摘を直すところまで自動で回したい場合は
  [self-review-loop](../self-review-loop/SKILL.md) を案内する（重大な指摘が 0 になるまで
  レビューと修正を繰り返す）。単発で直すだけなら `/code-review --fix` や手作業でよい。
- 自発的な起動。ユーザーが明示的に呼んだときだけ動く。
- コスト意識: 6 並列 subagent は相応にトークンを使う。巨大 PR では観点を間引く / 対象ファイルを
  絞る判断をユーザーに相談してよい。
